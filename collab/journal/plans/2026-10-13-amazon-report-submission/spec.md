# 실제 제보 접수 계약안

2026-10-13 · **승인 전 제안** · 담당 amazon

사용자가 선택한 첫 범위는 **익명 접수 + 첨부 저장**이다. PR #15의 입력 화면을 재사용한다. 로그인, 관리자 검토 화면, 제보 공개, 뉴스 자동 편입은 이번 범위에 넣지 않는다.

## 사용자 흐름

1. 카테고리·발생 시각·제목·위치·내용과 선택적 첨부를 입력한다. 발생 시각 입력에는 **한국시간**을 명시한다.
2. **제보 접수**를 누르면 브라우저에서 Go API로 보낸다. 전송 중에는 입력·삭제·제출을 잠근다.
3. 서버가 본문과 첨부를 모두 비공개 저장한 후 접수번호를 반환한다.
4. 유효한 접수 응답에만 **제보가 접수됐어요**와 접수번호를 표시한다. **새 제보 작성**을 누르면 입력과 첨부를 비운다.
5. 실패하면 입력과 첨부를 유지한다. 통신이 끊기면 **접수 여부를 확인하지 못했어요**로 안내하고, 같은 내용의 재시도는 같은 요청 키를 사용한다.

새로고침·탭 종료 후 제보 내용이나 요청 키를 복원하지 않는다. 익명 접수에는 본인 확인·접수 내역 조회 기능이 없다. 접수번호는 저장 결과 확인용이며 공개 조회 주소가 아니다.

## 요청과 응답

브라우저 환경 변수 `NEXT_PUBLIC_REPORT_API_BASE_URL`에는 공개 API 주소만 넣는다. 인증 비밀은 넣지 않는다. 운영 주소는 HTTPS이며 자격증명을 포함한 URL은 거부한다. 브라우저가 직접 `POST /reports`로 `multipart/form-data`를 전송하고, multipart boundary는 브라우저가 지정한다. 쿠키는 보내지 않는다.

| 항목 | 계약안 |
| --- | --- |
| `Idempotency-Key` | UUID v4. 미변경 재시도는 재사용, 내용·첨부 변경 후 제출은 새 키 |
| `category` | `society`, `security`, `politics`, `international` |
| `occurred_at` | RFC3339. 한국시간 입력을 UTC로 변환하여 전송 |
| `title` | trim 후 필수, UTF-16 코드 단위 100 이하 |
| `location` | trim 후 필수, UTF-16 코드 단위 200 이하 |
| `description` | trim 후 필수, UTF-16 코드 단위 5,000 이하 |
| `attachments` | 반복 파일 필드. 0~3개, 파일당 0 초과·10MiB 이하 |

첨부는 JPEG·PNG·WebP·MP4·WebM만 받는다. 서버가 선언 MIME과 파일 시그니처를 검사한다. 전체 영상/이미지 디코딩이나 악성코드 검사는 아니다. 원래 파일명은 메타데이터로만 저장하고 서버가 저장 파일명을 만든다. multipart 요청 전체는 32MiB로 제한한다.

새 접수는 `201`, 동일한 요청 키와 내용의 재시도는 `200`으로 아래 형식을 돌려준다.

```json
{
  "report_id": "0123456789abcdef0123456789abcdef",
  "status": "pending",
  "received_at": "2026-10-13T05:00:00Z"
}
```

`report_id`는 소문자 16진수 32자리다. 응답에는 본문·파일 경로·첨부 URL을 넣지 않는다. 같은 키에 다른 내용은 `409`다. 프런트는 `200/201`과 접수번호·상태·시각의 형식을 모두 확인한 뒤 성공으로 표시한다. 서버 내부 오류 본문을 그대로 표시하지 않는다.

## 저장과 운영

- 수집 뉴스·생성 이미지와 분리한 `REPORTS_DATA_DIR`에 제보별 JSON과 첨부를 저장한다. 공개 파일 라우트는 만들지 않는다.
- 기본 `REPORTS_ENABLED=false`. `REPORTS_ALLOWED_ORIGINS`에 정확한 웹앱 origin을 설정한 뒤 활성화한다. Origin 누락·불일치는 거부한다. CORS는 로그인이나 봇 차단 수단이 아니다.
- 제보 디렉터리 0700, 파일 0600. 같은 저장 볼륨의 임시 디렉터리에서 처리하고 전체 성공 후 원자적으로 게시한다. 디스크/업로드 오류가 나면 미완성 파일을 치운다.
- 제안 기본값은 저장 총량 1GiB(`REPORTS_MAX_STORAGE_BYTES`), UTC 일일 신규 접수 100건(`REPORTS_DAILY_LIMIT`), 동시 업로드 최대 2개다. 재시도는 새 접수 건수를 소비하지 않는다. 완료 파일 기준 저장 상한과 별도로 진행 중 임시 업로드의 여유 공간이 필요하다.
- Docker의 읽기 전용 루트 파일시스템을 유지하면서 `/data/reports` 영속 볼륨을 추가한다. Traefik에서 `/reports`의 POST/OPTIONS를 연결한다.
- 저장 용량·일일 수량 상한은 지출과 디스크 고갈을 줄이는 제한이다. 익명 서비스의 스팸을 완전히 막지는 못한다. 자동 삭제·운영자 조회 UI·파일 공개는 후속 정책으로 남긴다.

## 구현 및 검증 경계

프런트 `codex/report-submission`은 기존 PR #15 위에 쌓는다. Go `team-poem/poem-news`의 `codex/report-intake`가 실제 검증·저장·중복 방지 계약을 담당한다. 두 브랜치의 초안을 승인한 뒤 서버부터 구현하고 프런트를 연결한다.

직접 업로드를 택하면 큰 첨부를 Next 서버가 다시 받아 전달하지 않아도 된다. 단위 테스트 이후 실제 브라우저 → CORS → Go → 파일 저장 → 응답 흐름을 별도로 확인해야 한다. 현재 초안은 운영 서버를 활성화하거나 새 접수를 받지 않는다.

테스트와 기존 기준선 교체 내용은 [검토 제안](drafts/report-submission/proposal.md)에 모았다. 서버의 구체적인 오류 상태·저장 스키마·실행 테스트는 서버 저장소 `docs/drafts/report-intake/`가 담당한다.
