# 제보 요청 제한 시간·오류 복구 제안

2026-10-13 작성. **승인 전 정책·테스트 초안**이다. PR #16에 대한 solp721 리뷰를 구체화한다. 제품 구현, 운영 배포, 기존 승인 계획 재개는 수행하지 않았다.

기준은 `codex/report-recovery`의 `03a3857a89557ca3452b4a9c476aa5501d096d60`이며, 제품 코드는 PR #16의 `32a2a6a9ba519b2755815422e0a375df4072793d`와 같다. 기존 75개 테스트·helpers·fixtures·보관한 계약을 유지하고, 새 독립 파일 `src/app/report/report-recovery.test.ts`에 아래 6개 항목을 추가하는 안이다. `spec.md`, 기존 테스트 파일 또는 승인 상태를 변경하지 않는다.

## 검토할 정책

### 한 번의 제출에 60초

실제 요청 직전부터 응답 JSON 본문 읽기가 완료될 때까지 **단일 60,000ms 제한**을 적용한다. 같은 AbortController의 signal을 fetch에 전달하고, 응답 헤더를 받았다고 타이머를 다시 시작하거나 먼저 제거하지 않는다. 정상·실패 종료 시 타이머를 정리하며, 언마운트 시 진행 중 요청을 중단하고 남은 타이머를 정리한다.

가상 시계 테스트에서는 59,999ms까지 접수 중·잠금을 유지하고 60,000ms에 abort 및 불확실 안내·잠금 해제를 기대한다. 실제 브라우저의 백그라운드 타이머 지연까지 정확히 60초로 보장한다는 뜻은 아니다. 타이머가 실행되면 해당 시도가 더 이상 현재 접수 상태를 갱신하지 않도록 한다.

첨부는 기존 계약대로 최대 3개·각 10MiB, multipart 전체는 32MiB다. 조회 API의 5초 제한을 재사용하지 않는다. **60초는 이번 정책 제안이며, 최대 첨부 업로드 성능을 측정한 값이나 성공 보장 시간이 아니다.** 느린 업로드에서는 제한에 도달할 수 있다.

서버 담당자가 확인한 저장소의 Traefik v3.6 Compose에는 responding timeout 재정의가 없다. 공식 문서에서 `transport.respondingTimeouts.readTimeout` 기본값은 요청 본문 전체 읽기에 60초다. 브라우저 제한은 fetch 호출 시점부터 응답 본문까지이고 프록시 제한은 프록시가 요청을 읽는 구간이므로 시작점·측정 범위가 다르다. 두 값이 같다고 동기화되거나 프록시가 먼저/나중에 종료한다고 보장하지 않는다. **운영 인스턴스의 실제 실행 설정 확인·변경은 이번 범위가 아니다.** [Traefik v3.6 EntryPoints, 2026-10-13 확인](https://doc.traefik.io/traefik/v3.6/reference/install-configuration/entrypoints/)

AbortController는 요청뿐 아니라 응답 본문 소비도 중단할 수 있다. 별도 Chrome 실험에서도 헤더 대기와 HTTP 200 이후 본문 대기에 각각 AbortError가 확인됐다. 이것은 플랫폼 동작 근거이며 이 앱의 제보 기능 검증 결과는 아니다. [MDN abort(), 2026-10-13 확인](https://developer.mozilla.org/en-US/docs/Web/API/AbortController/abort), [플랫폼 실험 결과](probes/native-abort.json)

### 오류 경계와 작성 상태

설치된 `@suspensive/react` 3.21.4를 사용한다. 비동기 catch에서 `useErrorBoundary().setError(error)`로 제출 오류를 명시적으로 전달한다. **입력 폼 DOM·5개 값·첨부 File 객체·Idempotency-Key는 오류 경계 바깥에 유지하고, 제출 오류 패널만 로컬 경계의 fallback으로 표시**하는 안이다. 공통 AppShell 경계에 페이지 전체를 넘겨 작성 내용이 초기화되는 방식은 피한다. 새 의존성이나 공용 오류 경계 변경은 필요하지 않다.

fallback의 **오류 닫기** 버튼은 오류 표시만 reset한다. 폼·첨부·요청 키는 유지하고 자동으로 재전송하지 않는다. 사용자는 기존 **제보 접수** 버튼으로 다시 요청한다. 기존 테스트가 기대하는 대로 **오류 닫기를 누르지 않고도 같은 폼을 재제출할 수 있다.** 그 재시도가 다시 실패해도 새 오류가 실제 경계에 전달되고 입력 잠금이 풀려야 한다. 성공하면 이전 오류 fallback이 사라지고, 기존 접수번호 표시·성공 후 잠금을 유지한다.

기존 **새 제보 작성**은 성공 후 폼·첨부·키를 모두 비우는 별도 동작으로 유지한다. 새로고침·탭 종료·페이지 이탈 이후 복원이나 브라우저 영구 저장은 추가하지 않는다.

### 오류 분류와 요청 키

| 상황 | 안내·후속 동작 |
| --- | --- |
| 60초 만료, 연결 실패, 본문 읽기/파싱 실패, 잘못된 접수증, 5xx | `접수 여부를 확인하지 못했어요`를 포함한 안내. 작성 내용 유지, 잠금 해제, 같은 내용 재시도는 같은 키. |
| 정상 파싱된 확정 HTTP 오류(예: 413) | 기존 `제보를 접수하지 못했어요` 안내 유지. 내부 서버 응답 노출 없이 작성 내용 유지·잠금 해제. |
| 유효한 200/201 접수증 | 기존 성공 표시와 잠금 유지. 남은 deadline 정리. |
| 내용 또는 첨부 변경 후 제출 | 기존 계약대로 새 UUID v4 요청 키. |
| 오류 닫기 | 오류만 제거. 자동 전송·키 교체 없음. |
| 언마운트 | 진행 중 요청 중단·타이머 정리. 사라진 UI에 새 오류를 전달하지 않음. |

브라우저의 abort는 서버 저장 취소를 보장하지 않는다. 따라서 같은 내용의 재시도에 기존 키를 보존한다. 취소된 이전 요청의 늦은 완료가 새 요청의 성공·잠금·타이머를 바꾸지 않도록 하고, 정상적으로 abort를 따르는 Fetch를 대상으로 검증한다. AbortSignal을 무시하는 임의 전송기를 지원하기 위한 별도 경쟁 Promise 구현은 요구하지 않는다.

## 증거의 범위

테스트는 jsdom의 합성 submit/change 이벤트와 FileList 대용 배열을 사용한다. 실제 파일 선택 창, 브라우저 native validation, 모바일 키보드, 업로드 속도를 검증하지 않는다. File은 짧은 문자열 fixture이며 실제 PNG 시그니처·최대 용량 파일이 아니므로 서버의 파일 검사도 검증하지 않는다.

setTimeout/clearTimeout만 가상 시계로 제어한다. React·Suspensive 경계·원래 훅은 실제 실행하고 훅의 setError 호출만 관찰하는 부분 mock을 둔다. 기대한 오류의 React console 출력은 캡처하지만, Vitest의 미처리 예외·Promise 거부 감지는 끄지 않는다. fetch·response.json은 지연 Promise와 해당 signal의 abort 거부를 연결한 mock이며 실제 네트워크 호출은 없다. request signal의 유무·중단, 실제 fallback과 화면, 요청 키와 multipart를 함께 확인한다. 이것으로 운영 프록시·서버·CORS나 전체 브라우저 연동 성공을 주장하지 않는다.

기존 승인 계약에 포함된 것은 실패 시 값·파일 유지, 불확실 안내, 동일/변경 내용의 요청 키, 성공 후 잠금이다. 이번에 추가로 승인할 기준은 **60초 전체 deadline, AbortController와 본문 지연 처리, 로컬 Suspensive fallback/reset과 상태 유지, 관련 정리·지연 검증**이다. 정확한 제안과 7개 실행 블록을 검토·승인한 뒤 새 기준을 등록하고 구현을 진행한다.
